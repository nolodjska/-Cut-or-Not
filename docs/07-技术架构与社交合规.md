## 0. 摘要

- **平台定调**：微信"游戏"类目与小游戏**必须版号**。Demo 只发 **H5**（自有域名 + 局域网 + 扫码），小程序入口在拿到版号前不做。此条决定全部排期。
- **一份引擎跑两端 + 权威边界**：`engine` 纯函数 + 注入 `clock`/`rng`，零依赖、无 DOM、无 `wx.*`、无 `Date.now`、无 `Math.random`；H5 与小程序各挂 ≤200 行 adapter（storage/clock/rng/net/share），体积 ≤300 KB 未压缩 / ≤90 KB gzip（提议值（待校准）），满足小程序主包 2 MB。服务端权威「钱、货、地、单、价、果、随机」；客户端只预测「标量与动画」，订单簿/成交/随机/所有权**不预测**。
- **生长必须惰性结算**：只存 `planted_at + grow_s + last_settle_at + pending_mods` 推导当前态。6000 地块全量扫描 = **100 次/秒常量**；懒结算 = **0.7 次/秒**，差 **145 倍**，且成本与活跃玩家数成正比。成熟通知走独立 `due:{s}` 队列，实测 **13 次/分钟**。
- **随机采纳 04 规范**：`FNV-1a64 + splitmix64 + 字段级子流`，种子只存字符串 `GG-{7}{1}`（Crockford Base32）+ `SEED_VERSION=GGv1`，**不存配置快照**。验收：1000 种子两端 diff = 0；同版本重放 diff = 0。
- **DB 分三层**：局内 OLTP（16 主表 + 6 补充）／跨局账户层（与局内**物理隔离**，04 硬要求）／结算消费层（05 的 `fact_*` 设计代号全部映射到本文物理列，§3.1）。
- **05 的 4 个阻塞级缺口已补齐**：`G1 init_net_worth_milli`（t0 冻结，4 个奖的分母）、`G3 price_after_5m_milli`（成交后 5 分钟异步回填）、`G6 pair_pnl` 表（FIFO 平仓回合结果，另配 `holdings_lots` 作机制层）、`G11 craft_start/craft_done` 事件。事后算不出的量必须排期：见派生调度器（§2.6，峰值飞行 15000 条，worker 50 条/秒）。
- **合规红线落在词表**：60+ 禁用词（投资/理财/收益/提现/充值/钱包/股票/K线/做空/杠杆/保证金/爆仓/割韭菜/洗钱/下注/抽奖…）全替换（§2.8.3）；**邀请机制零奖励**（避诱导分享）；"不构成赌博"答辩段落 §2.8.4 可直接引用。
- **社交缓解是字段不是原则**：匿名赛季默认开、针对同一对手 24h 上限 3 次、结算页不出名次数字、被收购者得遗产（净值 12% 上限 300 + 自选天赋 + 仇敌档案）、好友房不计排名。
- **Demo 结论**：单文件 H5 + 无后端 + localStorage **能验证核心链条 5/6**（种地/市场/打压/破产/收购 ✓，真人社交博弈 ✗）→ v0.1 先做单机（1-2 周），v0.2 再联机，engine 接口全程不变（§2.10.4）。
- **容量**：1000 玩家 / 50 QPS 峰值下 Redis ≈ **900 ops/s（<1%）**、撮合 CPU **<4% 单核**、Redis 内存 <200 MB、PG **约 230 万行/赛季**。**唯一瓶颈是 WS 扇出**：不合并 = 50000 msg/s（过载），按 250 ms 合并 = **4000 msg/s**（安全）。一台 2 vCPU/4 GB（¥70-150/月（提议值（待校准）））可承载。

## 1. 评审：问题与风险

- **[P0] 微信游戏类目需版号，非游戏类目会被驳回或下架。** 为什么：以游戏玩法为核心即须选"游戏"类目/小游戏，需版号或《网络文化经营许可证》，放"工具/模拟经营"属类目错配 → 建议：Demo 只发 H5；版号路径（6-12 个月、自办 3-5 万元（提议值（待校准）））与开发并行，把"小程序发布"从 Demo 里程碑删除。

- **[P0] 「洗钱、内幕交易、操纵市场」是刑法/证券法罪名描述。** 为什么：冻结案 §4.3/§5.4 直接使用且机制就是其游戏化，审核方只需判定"不良导向" → 建议：机制全留、**词面全换**（§2.8.3）。必改冻结案措辞项，不回改 00，仅在此记录。

- **[P0] 「邀请得奖励」是微信《诱导分享》红线，会封链/封域名。** 为什么：同学局天然靠群分享，极易顺手做成"邀 3 人得稀有种子" → 建议：邀请 token 只带 `room_id + inviter_id`，**接口层不允许存在邀请奖励写操作**（§2.7 + CI 检查）。

- **[P0] 客户端权威 = 3 天经济一夜被刷穿。** 为什么：H5/小程序端一切可改（localStorage、断点、重放）→ 建议：服务端权威六项 + 15 条校验（§2.8）。同构引擎的价值正在于此——客户端跑"预测副本"，服务端跑"权威副本"，同一份代码。

- **[P0] 跨分支冲突一：NAV 定义 02 与 05 不一致。** 为什么：02 定义「库存 = 现价 × 流动性系数」，05 §2.13 定义 `VAL = median(MID_30m_TWAP, FV, BID)`（明确不用单一价以防自成交拉价），同一局 A 胜利会算出两个数 → 建议：**以 05 为准**（结算分支拥有判定权），02 口径降级为展示用；SYS 只暴露一份 `VAL`，禁止第二处实现（§3.2）。

- **[P0] 跨分支冲突二：垄断分母「流通量」02 与 05 不一致。** 为什么：05 定义 `F(c,t) = Σ库存 + 挂单 + 做市库存（不含在地未收割）`（时点），02 提议「全场库存 + 24h NPC 净吸纳 ×0.5」（滚动），60%/55%/50% 判定结果不同 → 建议：判定用 05 时点口径；02 的「对倒不计入分子分母」作为**反作弊过滤**保留（不冲突）；24h 值列展示口径。Q-SYS-06。

- **[P0] 跨分支冲突三：初始净值 02 与 03/04 相差 10 倍。** 为什么：02 §0 写「六家初始 NAV 全部 = 10,000」，04 §0 写「初始净值 1000（现金 800 + 4 地块 × 50）」，03 写「上限 300（= 初始资产 30%）」反推 1000；A 胜利"3 倍"两种口径含义完全不同 → 建议：采 **1000**（03 与 04 一致，2:1），02 的 10,000 疑为单位换算误差。Q-SYS-05。

- **[P0] 加权平均成本支撑不了 05 的 FIFO 配对盈亏。** 为什么：05 §2.9「韭菜收割机」需要 `pnl_pair(q→p)` = 对手方在**与 p 成交对应的平仓回合**中的盈亏，须 FIFO 逐笔匹配持仓批次；只存 `avg_cost` 即丢失批次信息、**事后不可重建**，结算成本从"一次聚合"变成"一次全量模拟" → 建议：`holdings_lots`（lot 明细）+ `pair_pnl`（平仓回合结果表）在 v0.1 就落，`holdings` 只作聚合缓存。已补为 G6（§3.1）。

- **[P1] 05 要的是一批「延迟派生量」，不排期就永远算不出来。** 为什么：`price_after_5m_milli`、`TWAP_6h/24h`、NAV 快照、`intel.outcome` 都是"未来才知道"的值 → 建议：**派生指标调度器**（`due_derive` ZSET + 单 worker），峰值飞行 15000 条、worker 50 条/秒即够（§2.6）。

- **[P1] 04 要求「跨局与局内数据物理隔离」，混表会让 K1-K7 白名单无法执行，04 的「跨局加成 ≤ +5%」也无法验证。** 建议：`account_*` 与 `season_*` 两套表 + 只读视图 `v_account_bonus`（§2.5）；校验 `state_hash` 不含任何 `account_*` 字段。

- **[P1] 「破产即本局结束」（冻结案 §7.4）与 03/05 都冲突。** 为什么：05 需破产者参与「最悲情破产者」并二次推送，03 §0 明确"破产不禁赛（保留 1 块免租地块，可继续交易）"；按原案破产者在 3 天局后半程流失，结算画面无人看 → 建议：破产 ≠ 退出，`status='bankrupt'` 仍可交易、可被收购、可看结算，破产瞬间推送「预结算卡」。

- **[P1] 拉黑若阻断经济交互会把 6 人局市场切成两半。** 为什么：经济交互是核心不是社交；阻断后流通量被人为割裂、垄断门槛失真，且拉黑变成"拒绝被收购"的战术盾牌 → 建议：**拉黑只作用于社交面**（聊天/邀请/昵称显示/结算同屏），不影响撮合；叠加 03 的"排行房社交关系隔离 + 好友房不计排名"。

- **[P1] 拍卖倒计时在客户端 = 改表即可无限延长出价窗口。** 为什么：冻结案 §6.2「允许狙击」+ 移动端 P99 往返 800 ms，无服务端权威时钟则"公平"无法定义 → 建议：采纳 03 —— 唯一权威时钟 = 服务端 Unix 毫秒；软延时 30 s × ≤6 次；**强制代理出价**排除网速/手速变量；客户端只显示。

- **[P2] localStorage 5-10 MB 会被价格历史与事件日志撑爆**（1 点/秒 × 3 天 = 259200 点/作物）。建议：价格降采样为 1 分钟 1 桶（3 天 = 4320 点/作物，约 400 KB）；`events` 环形只留 2000 条；`command_log` 紧凑数组编码（<150 KB）。

- **[P2] 热态与合规的两个默认缺失。** ① 每笔交易后 O(玩家数) 重算份额，1000 人时 5 万次比较/秒 → 用 `share:{s}:{crop}` Hash 增量维护（`HINCRBY` O(1)），垄断检查一次 `HGETALL`（3 次调用，不随人数增长）；② 未成年人保护与个人信息最小化默认缺失（小游戏强制实名 + 防沉迷，同学局大概率有未成年）→ Demo 不采集真实身份信息，显示名用服务端生成的 `display_alias`，H5 用服务端下发 `guest_id`。

### 2.1 双端同构与权威边界

**分层与依赖方向（单向，CI 强制）**

```

          market company intel auction(5阶段) endgame(终局倒计时) metrics reduce(state,cmd,ctx) sim
```

CI 守卫：`grep -rE "Math\.random|Date\.now|performance\.|document|window|wx\.|localStorage|fetch" src/engine` 必须为空；`engine` 不得 import `ui|ai|net|persistence|platform`；依赖方向不可逆。

**单位与定点**：金额/数量 `_milli`（1000 = 1 金）；比率 `_bp`（10000 = 100%）；时间毫秒整数 `_ms`（只用服务端时钟）；乘法 `mul(a_milli, b_bp) = trunc(a_milli * b_bp / 10000)`，取整方向固定向零并在测试中断言。禁小数参与逻辑，`toFixed` 仅允许在 ui 层。

**权威边界表**

| 状态项 | 权威 | 客户端可预测 | 容差 | 纠错 |
|---|---|---|---|---|
| 现金 / 持仓 | 服务端 | 可（乐观显示） | 500 ms | `state_version` 覆盖 |
| 地块与生长进度 | 服务端（`planted_at` 只由服务端写） | 可（本地外推，两端口径一致） | 无上限 | 响应带 `server_ts_ms`，重算 offset |
| 成熟倒计时 | 服务端时间 | 可 | ±2 s（提议值（待校准）） | 最近 5 次采样中位数偏移 |
| 挂单 / 订单簿 | 服务端 | **否** | — | WS 快照 1 s |
| 成交 / 所有权 / 破产 | 服务端 | 否 | — | 事件推送 |
| 最新成交价 | 服务端 | 视觉插值 | 250 ms | `price.tick` 覆盖 |
| 随机结果（天赋/事件/情报/产出） | **服务端 roll** | 否 | — | 返回 `roll_seed + result`，可审计 |
| 拍卖倒计时 / 出价 / 代理上限 | 服务端 | 显示可、判定否 | ±2 s | 服务端 `ends_at_ms` |

### 2.2 确定性随机（对齐 04）

采纳 04：`FNV-1a64 + splitmix64 + 字段级独立子流`，输出万分位整数。JS 无高速 64 位整数（BigInt 在小程序端不可用/极慢），故用 **hi/lo 双 uint32** 实现 64 位算法。

```js
function fnv1a64(str) {                      // -> [hi, lo]，FNV basis 14695981039346656037
  let hHi = 0x84222325, hLo = 0xcbf29ce4;
  for (let i = 0; i < str.length; i++) {
    hLo ^= str.charCodeAt(i);                // ASCII 输入只需异或低 32 位
    const p0 = Math.imul(hLo, 0x1B3) >>> 0;   // ×1099511628211 = 0x100000001B3
    const p1 = (Math.imul(hHi, 0x1B3) + Math.imul(hLo, 0x100)) >>> 0;
    hLo = p0; hHi = p1;
  }
  return [hHi >>> 0, hLo >>> 0];
}
function splitmix64(hi, lo) {                // 状态与输出均 64 位；取高 32 位做权重足够
  const c = 0x9E3779B9;
  lo = (lo + c) >>> 0; hi = (hi + (lo < c ? 1 : 0)) >>> 0;
  let zHi = hi, zLo = Math.imul(lo ^ (lo >>> 16), 0x85EBCA6B) >>> 0;
  zHi = Math.imul(zHi ^ (zHi >>> 13), 0xC2B2AE35) >>> 0;
  return [zHi, (zLo ^ (zLo >>> 16)) >>> 0];  // 需按 04 规范补齐 xor-shift 步骤后冻结
}
function fieldRng(seedStr, field) {          // 每 field 一个独立实例，改一个字段不雪崩
  const [Hh, Hl] = fnv1a64(seedStr), [Fh, Fl] = fnv1a64(field);
  return splitmix64(Hh ^ Fh, Hl ^ Fl);
}
```

字段清单（04 的 F1-F9）：`F1 作物池 / F2 市场规则变异 / F3 NPC 人格 / F4 事件池权重 / F5 初始资源偏移 / F6 每作物初始价格偏移(×0.85-1.15) / F7 地块品质 / F8 情报真伪种子 / F9 外观文案变体`；SYS 追加 **`F10 market_tick`**（价格噪声与事件触发，必须独立，否则新增事件类型会改变历史价格序列）→ 待 04 确认，Q-SYS-09。

硬约束（CI）：禁 `Math.random()`→`fieldRng`；禁 `Date.now()`→注入 `clock`；`Object.keys/Set/Map` 迭代顺序不得参与逻辑（先排序成数组）；禁 `for...in`；禁小数参与金额/数量；**禁存配置快照**（只存 `seed` + `SEED_VERSION`，配置永远由算法还原，04 的 C5）。
验收：① 1000 个种子在 Node 与浏览器两端配置 diff = 0；② 同 `SEED_VERSION` 重放 `state_hash` diff = 0；③ `save→load→save` 两次 JSON 逐字节相等。

| `cash`/`debt` / `hold:*` | 成交/还贷/收购/收获 | ~100/s · ~150/s | 单键自增，Lua 原子；Hash field 增量 |
| `plot:*` | 播种/收获/懒结算 | 0.7/s + 0.2/s | §2.4 |
| `share:*` / `fvhist:*` | 每成交 / 定时 | 50/s · 0.05/s | `HINCRBY` O(1) / 流通量历史 |
| `ev:*` | 所有写操作 | ~100/s | Stream，多消费者 |
| `due:*` / `due_derive:*` | 播种 / 成交后 5min | 13/min · 峰值 50/s | §2.4 / §2.6 |

**原子性**：一笔成交（`ob`+`ord`+`cash`+`hold`+`short`+`share`+`lots`+`ev`，约 12-20 命令）放进**单个 Lua 脚本**；不用 MULTI/EXEC（事务内无法读中间结果做分支）。

### 2.4 作物生长：惰性结算

**为什么不能全量扫描**：6000 地块每分钟扫一次 = `6000×1440 = 8.64M` 次/天 = **100 次/秒常量**（99.9% 空转）；懒结算实际触达（1000 人 × 20 次访问/天 × 3 地块 ≈ 6 万次/天）= **0.7 次/秒**。差 **145 倍**，且成本与**活跃玩家数**成正比——赛季后期玩家离线增多时自动下降。

地块只存决定态的量：`crop_id, grow_s, planted_at（服务端写，不可变）, pause_total, last_settle_at, mod_stack, pending_mods`；`stage/progress` 只是派生缓存。

```js
function settlePlot(plot, nowMs, world) {            // 纯函数：同入参必得同出参
  const elapsed = Math.max(0, nowMs - plot.planted_at) - plot.pause_total;
  const ratio   = elapsed / (plot.grow_s * 1000);     // 只用整数毫秒；金额禁止浮点
  const stage   = ratio >= 1 ? 3 : Math.floor(ratio * 4);  // 0播种 1生长 2成熟前 3可收
  const [due, later] = partition(plot.pending_mods, m => m.t_eff <= nowMs);  // 只应用已生效
  const mult_bp = mulBp([...plot.mod_stack, ...due.map(m => m.k)]);          // 乘区全 bp 整数
  const yield_milli = stage < 3 ? 0
      : mulMilli(world.base_yield_milli[plot.crop_id], mult_bp)
        * overripeFactor(nowMs - maturedAt(plot), world); // 超 2×grow_s 线性衰减到 60%（提议值（待校准））
  return { ...plot, stage, pending_mods: later,
           mod_stack: [...plot.mod_stack, ...due.map(m => m.k)], yield_milli, last_settle_at: nowMs };
}
```

1. **纯函数** —— 这是「客户端可预测」与「服务端可重放」的共同前提。
2. `pending_mods` 按 `t_eff` 升序，应用后固化进 `mod_stack`，避免重复计入。
3. **成熟通知不能靠懒结算**（玩家不访问则永不触发）：播种时 `ZADD due { planted_at + grow_s*1000 }`，每 10 s（提议值（待校准））`ZRANGEBYSCORE due 0 now LIMIT 0 200`，**只推通知不改状态**。实测 ≈13 次/分钟。
4. **过熟衰减**必须有，否则"永不收割"无成本，破坏"割不割"这个名字的张力。

**并发更新顺序**
① 单写者：改 `plot` 前先 `lock:{plot_id}`（`SET NX PX 3000`）。② 锁内：读 → `settlePlot(now)` → 校验动作 → 写回 + 必要时 `ZADD due` → 写 `ev` → 释放。③ 批量收割按 `plot_id` **升序**加锁避免 AB-BA 死锁；拿不到第 2 把锁则回滚第 1 把（不等待）。④ 全局顺序：**地块（产出）→ 持仓 → 订单簿 → 价格 → events**；价格是聚合量必须最后算，否则同一笔被计入两次供应。⑤ 撮合确定性：同毫秒多笔按 `(price 优先, server_ts, seq)` 排序，`seq` 由 `INCR` 单键发号，结果唯一。⑥ 幂等：`idem:{pid}:{key} SET NX EX 1800` 成功才执行，重复请求返回上次结果。⑦ Lua 内不做网络/DB IO；成功后异步落库（`ev`→消费者→PG），失败重试 5 次后进死信表。

### 2.6 派生指标调度器（本分支新增，05 的硬依赖）

05 需要的量分两类：**即时量**（成交时算得）与**延迟量**（未来才知道）。延迟量必须排期，事后不可重建。

| 派生任务 | 排期时机 | 到期动作 | 量级 |
|---|---|---|---|
| `price_after_5m(trade_id)` | 每笔成交 `ZADD due_derive +300000` | 读该作物 mid 回填 `trades.price_after_5m_milli`（**G3**） | 峰值飞行 **15000 条**（50 QPS×5min）；worker 50 条/s |
| `twap_rollup(crop)` | 每 60 s | 由 `bar1m` 算 `twap6h/twap24h/fv/bid/ask` 写 `px:*:twap`（03 抵价计价、05 的 VAL 都用） | 3 作物 × 1/min |
| `nav_snapshot(company)` | 每 300 s | 按 05 §2.13 全式算 NAV；`hour_index` 整点写 `player_metrics_daily` | 1000/300 = **3.3 次/s**；每次约 15 读 → +50 ops/s |
| `nav_twap6h(company)` | 每 300 s | 由 6 h 内 72 点算 `TWAP_6h(NAV)` 供 A 胜利取值 | 同上 |
| `snap_float(crop)` | 每 300~3600 s | 写 `snap_float`（流通量历史 + 头名占比） | ≤3/min |
| `intel_outcome(intel_id)` | 成交时按 `window_end` 排期 | 求值 `predicate` 写 `outcome` + 回填 `consensus_prob_bp`（**G5**） | <1/s |
| `pair_pnl_close(lot_id)` | FIFO 平仓回合结束时 | 写 `pair_pnl`（**G6**） | 随交易量 |
| `tau_c_daily(crop)` | 每 86400 s | 当日 1 min 位移分布取 P75 写 `crops.vol_noise_tau_bp`（**G2**） | 3/天 |
| `obs_delayed(co)` | 终局倒计时每 60 s | 写 `obs:{s}:{co}`；联盟成员读 **30 分钟前**快照（05 §2.11 延迟视野） | 仅 endgame 期 |

实现：单进程 worker，每 1 s `ZRANGEBYSCORE due_derive 0 now LIMIT 0 200`，执行后 `ZREM`；失败 `ZADD` 重试（≤5 次，退避 2^n s）。任务只存 `type + args + due_ms`，**不存状态快照**——读时取最新值，正是"延迟 5 分钟看 mid"的语义。为什么不做事后重算：需要完整历史行情与持仓回放，代价 O(全量事件)；调度器把它压成 O(1) 次读取（§1-R8 的量化依据）。

**「为什么不构成赌博」——可直接用于审核答辩**

> 《割不割》是一款以虚拟农业经营为题材的休闲策略游戏。本产品**不设任何充值入口**，玩家无法以任何货币购买游戏内的资源、道具、随机机会或数值优势；本产品**不设任何提现、兑换、转账通道**，游戏内货币「金」仅为本作虚构世界的数值记录，**不存在任何与现实财物挂钩的兑换途径**，赛季结束后统一清零、不具备现实价值，且不可在玩家之间转让。
>
> 本作的随机机制（每局世界种子、天赋三选一、市场随机事件、作物产出浮动）**全部免费触发**，不对应任何付费行为，且概率与算法在游戏内「概率说明」页完整公示。随机的对象是**游戏体验的多样性**（每局可用天赋与规则变异不同），而非玩家之间的财物输赢：随机结果不产生任何一方对另一方的财物得失。
>
> 本作的竞拍会、买卖、收购均为**玩家之间在游戏内虚拟道具与虚拟数值上的策略互动**，结果不构成对任何现实财物的占有或转移，不存在输家向赢家支付现实价值的机制。
>
> 依据《刑法》第三百零三条及相关司法解释，赌博的构成需同时具备"以营利为目的""以财物为赌注""输赢具有偶然性并导致财物转移"三个要件。本产品无充值/提现通道，玩家投入的时间与取得的虚拟数值均无法转化为现实财物，**不存在"以财物为赌注"与"财物转移"**，因此**不构成赌博**，亦不涉及任何证券、期货、基金等金融业务。


### 2.11 性能量级估算

假设：1000 玩家（约 167 个 6 人房）、峰值并发交易 **50 QPS**（提议值（待校准））、3 作物、6 地块/玩家 = 6000 地块。

| 项 | 量级 | 说明 |
|---|---|---|
| 价格 tick（按需重算 + 1 Hz 快照，推荐） | 空闲 3 ops/s（只写 hist） | 单次计算 <5 µs（无 IO）；3 作物×1 Hz 的 CPU <0.002% |
| 交易校验 + 撮合（平均吃 5 档） | 0.15 + 0.5 ms/笔 → **3.25% 单核** | 全内存态无 DB；ZSET 深度通常 <30 |
| Lua 原子写（12-20 命令） | **600-1000 ops/s** | Redis 单实例 100k+ → **<1%** |
| 落库（异步批） | trades 1 + holdings 2 + lots 2 + events 1 = **300 行/s**，500 ms 批提交 → 8 事务/s | PG 单核 <5% |
| 派生排期 + NAV 快照 | +50 + 50 ops/s | 飞行 15000 条；1000 人/300 s |
| **Redis 合计** / **CPU 合计** | **≈900 ops/s（<1%）** / **<4% 单核** | 可支撑至约 600 QPS 才需多核；**撮合不是瓶颈** |
| WS 扇出（不合并） | `50×1000 = 50000 msg/s` | ❌ 超出单 Node 合理负载（20-30k msg/s） |
| **WS 扇出（250 ms 合并，推荐）** | `4×1000 = 4000 msg/s` | ✅ 约 480 KB/s；叠加按作物订阅降至 2400 msg/s；分片（20 进程）后每进程 200 msg/s |
| WS 连接内存 | 30-50 KB/连接 → 1000 连接 ≈ 30-50 MB | 单进程建议上限 3000 连接（提议值（待校准）），超过按 `season_id` 分片 |
| Redis 内存 | ~6 MB 数据 + `ev` MAXLEN 200000×~300 B ≈ 60 MB → **<200 MB** | 实例给 1 GB（留 fork COW 余量） |
| PG 数据量 | trades 9 万 + events 90 万 + lots 18 万 + pair_pnl 9 万 + logs 30 万 + metrics/nav 86 万 = **约 240 万行/赛季** | 3 天内 <2 GB；1 vCPU/1 GB 起步 |
| 服务端实例 | **2 vCPU / 4 GB**，约 ¥70-150/月（提议值（待校准）） | Demo 可同机跑 Node+Redis+PG；正式版至少 2 机 |
| 定时/惰性开销 | 全量扫描 8.64M/天（100/s 常量）→ 懒结算 0.7/s；到期队列 0.2/s | 懒结算降低 **145 倍** |

## 4. 待决问题清单

**Q-SYS-01 微信小程序还要不要做、什么时候做？** 必须人定：这是钱与排期的决定（版号 6-12 个月、3-5 万元），不是技术决定 → 推荐默认：Demo 只发 H5，版号路径与开发并行｜备选：先发"非游戏类目"小程序｜后果：备选大概率被驳回或上线后下架，且影响主体后续提审信用；默认则短期无法在微信内直接传播，靠链接/二维码。

**Q-SYS-02 NAV 快照频率取多少（05 的 `TWAP_6h(NAV)` 依赖它）？** 必须人定：直接决定 PG 行数与计算成本 → 推荐默认：**5 分钟 1 点**（6 h = 72 点，精度足够；1000 人 × 864 点 = 86 万行/赛季）｜备选：1 分钟｜后果：1 分钟则存储与写入 ×5（430 万行/赛季），收益仅小幅平滑；15 分钟则 6 h 仅 24 点，TWAP 对尖峰不敏感，A 胜利取值可能偏离玩家体感。

**Q-SYS-03 NPC 能否获得提名与称号？（02 与 05 冲突）** 必须人定：涉及"人人被记住"的荣誉分配 → 推荐默认：**采纳 05** —— NPC 可获奖、绝不可获首席，获奖切「机构版」语气｜备选：NPC 完全不参与提名（SYS 原提议）｜后果：默认则依赖系统实装的奖（如最佳情报商）在玩家不参与时由 NPC 收下、避免空奖，但可能被认为"机器拿奖"；备选需 05 改兜底逻辑，且部分奖在 3 真人局必空。

**Q-SYS-04 02 的 6 条公司资源条：单 JSONB 还是 6 张表？** 必须人定：影响 schema 稳定性与查询能力 → 推荐默认：`companies.state_json` 单 JSONB + GIN 索引｜备选：6 张独立表｜后果：默认则"按资源值排行取 Top"需额外表达式索引、偶发慢查询；6 表则每次读公司 6 处 JOIN、迁移成本 ×6。唯一例外：需高频排行的资源单独提列。

**Q-SYS-05 初始净值是 1000 还是 10,000？（02 与 03/04 冲突）** 必须人定：A 胜利"3 倍"的含义完全取决于此 → 推荐默认：**1000**（03/04 一致）｜备选：10,000｜后果：若定 10,000，则 03 的复仇上限 300 与 04 的"初始资产 30%"全部要改（300→3000），且 02 的日注入 40,000 会变成 4 倍初始资产/天，经济瞬间通胀。

**Q-SYS-06 垄断分母用 05 的时点 `F(c,t)` 还是 02 的 24h 滚动口径？** 必须人定：直接决定 C 能否达成，两口径在 3 天局里差异可达 5-10 pt → 推荐默认：判定用 05 的时点口径（结算分支拥有判定权）｜备选：02 的滚动口径｜后果：滚动更抗操纵（判定瞬间搬货无效）但需维护 24 h 窗口聚合，且与 05 全部算式不兼容（`Prox`、`Ctrl` 都按时点定义）。

**Q-SYS-07 02 的 D 路径「四项最低项 ≥ 全场中位数 1.2 倍」与 05 的「四项均 ≥0.20 + 全服最大值归一」如何统一？** 必须人定：归一基准不同（中位数 vs 最大值），D 达成率差异大 → 推荐默认：判定用 05，02 的 1.2× 中位数降为**提示文案**（"你的短板偏低"）｜备选：以 02 为准｜后果：中位数归一在"全员摆烂"局会放松门槛（中位数低→易达标），最大值归一不受此影响；但 05 口径会让 D 在"某人四项碾压"的局里更难达成。

**Q-SYS-08 冻结案的「离线价格波动减半」如何落地？** 必须人定：按玩家分叉价格会崩坏全局价格 → 推荐默认：价格全局唯一，离线保护作用于**成交端**（离线期间挂单不成交或滑点扩大 2×），回归补发 `offline_span` 梯度｜备选：为用户维护"个人价格快照"｜后果：备选则世界不唯一，垄断判定与持仓估值崩坏，服务端需维护 N 份价格（内存与复杂度上升一个量级）；默认需数值分支重调"离线"的经济含义（放置收益来自作物生长而非价格保护）。

**Q-SYS-09 04 的字段子流是否增加 `F10 market_tick`？** 必须人定：04 规定 9 个字段，SYS 发现价格噪声无处安放 → 推荐默认：增加 `F10`（价格噪声与事件触发），保持"新增功能不改历史序列"｜备选：并入 `F4`（事件池权重）｜后果：选备选则未来新增事件类型会改变 F4 历史抽取序列，破坏重放与两端 diff=0 的验收；选默认需 04 更新字段清单与 `SEED_VERSION` 升级策略。

**Q-SYS-10 拉黑是否阻断经济交互？** 必须人定：社交安全 vs 市场完整性的取舍 → 推荐默认：**不阻断**（仅聊天/邀请/显示/结算同屏生效）｜备选：阻断｜后果：阻断则 6 人局市场被人为切分、垄断份额失真，且拉黑变成"拒绝被收购"的战术盾牌，与收购核心爽点冲突；默认则用户可能觉得"拉黑了还能被坑"，需文案解释"商场上没有私怨，只有买卖"。

**Q-SYS-11 天赋抽取的软保底如何公示（04 已定机制）？** 必须人定：做了保底必须在概率公示页写明（合规要求）→ 推荐默认：明文公示 04 的规则（连 2 次无稀有 → 第 3 次强制稀有+ + 每局 1 次免费重抽），并展示 `SEED_VERSION` 与天赋池版本号｜备选：只公示基础权重｜后果：备选属公示不完整，若被投诉"概率不透明"无法自证；默认只需加一段静态文本，成本近零。

**Q-SYS-12 是否需要交易手续费抑制刷量？** 必须人定：手续费是经济平衡阀，直接改变"逼仓"的成本结构，且需与 02 的日注入 40,000 联合校准 → 推荐默认：双向 `fee_bp = 50`（0.5%），最低 1 金；自成交额外加收 200 bp 惩罚费率（并已被自成交拦截兜底）｜备选：零手续费｜后果：零费则"自己跟自己买卖"零成本，可刷价格与"城市奠基人"成交量，需额外拦截规则；收费则降低高频交易意愿，需 02 确认不会让逼仓不划算。

**Q-SYS-13 玩家能否中途加入赛季？** 必须人定：影响房间补位与流通量公平性 → 推荐默认：允许开局后 24 h 内加入，按剩余时间折算初始资产（按 70% 起步（提议值（待校准））补偿信息落后）；已破产/被收购玩家不退出房间（03 已判决不禁赛）｜备选：开局即锁房｜后果：锁房则同学临时缺人无法补位；允许加入则需处理"中途加入者份额从 0 起步"的数值问题，且可能被用于"小号进场接盘"（需限制同 `device_id` 最多 1 个真人账号）。

**Q-SYS-14 事件流与明细数据的保留策略？** 必须人定：影响可回放性（审计/客服/05 提名复核）与存储成本 → 推荐默认：Redis `ev` MAXLEN 200000；PG `events/trades/lots/pair_pnl` 保留 1 个赛季 + 归档 90 天（与 05 §3.6 一致）；`logs` 7 天；`price_tick` 类 30 天；`snap_*`、`settlements`、`claims` 永久｜备选：全量永久保留｜后果：默认下"上赛季逐笔复盘"需从归档恢复（约 1 天延迟）；永久保留则约 240 万行/赛季 × 每赛季 3 天 → 1000 人规模每年约 30-50 GB，成本可接受但极少被查询。

**Q-SYS-15 定点精度口径最终用 `_milli`（1e-3）还是 04 的万分位（1e-4）？** 必须人定：影响 4 个分支的公式与全部历史数据（05 已按 `_milli` 落笔）→ 推荐默认：**金额/数量 `_milli` + 比率 `_bp`，万分位只用于配置系数与 PRNG 输出**（1e-6 相对分辨率足够，且改动最小）｜备选：全链路 1e-4｜后果：现在改是 1 次全量重命名；上线后改要动 4 个分支的公式与历史数据（不可逆）。若 04 坚持全链路万分位，需在 Demo 开写前定，否则 Demo 存档 schema 也要跟着改版。
