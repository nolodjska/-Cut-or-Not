## ① 现状证据

### 1.1 一句话结论

**`holdings` 是"骨架已埋、血肉全无"的状态。**

- 结构存在、语义在 `docs/13 §7.2` 定义了，但 **`stake` 在整个引擎里没有被读过一次**（只在 UI 里被读来显示）。
- **没有**股东名册函数、**没有**决议对象、**没有**投票动作、**没有**股份转让动作。
  `game/parts/` 下与治理相关的符号为零；唯一的"投票"字样是三条注释和一个 glyph 分支。
- 玩家与 NPC 的控股关系**完全不存在**：每个玩家（含 NPC）的 `holdings` 恒为自己那 1 家公司（`stake=control=1`）。
- 2026-10-08 刚落地的"NPC 提案通道"（信匣合作/收购通知）**已经把 `m.actions` 这个插槽留好了**，
  这是决议邮件唯一该复用的接口——但它是**空插槽**，注释明确写着"决议是下一刀，这里不伪造"。

### 1.2 `holdings` 的结构与语义

**唯一创建点**：`game/parts/03-core.js:168`

```js
holdings: [{ corpId: corp.id, stake: 1, control: 1, debt: 0, bankrupt: false, acquiredAt: 0 }],
```

| 字段 | 定义位置 | 含义（文档口径） | 谁写 | 谁读 |
|---|---|---|---|---|
| `corpId` | `03-core.js:168` | 标的那家公司 id | `03-core.js:168`（开局） | `05-firm.js:9`、`14-npc.js:171`、`17-ledger.js:82` |
| **`stake`** | `03-core.js:168` | **持股比例（分红权）**（`docs/13 §7.2` L240） | `03-core.js:168`（恒 1） | **引擎：无人读**；UI：`17-ledger.js:93`（仅显示） |
| **`control`** | `03-core.js:168` | **控制权（决策权，可 > stake）**（`docs/13 §7.2` L240） | `03-core.js:168`（恒 1） | `05-firm.js:10`（并表加权）、`17-ledger.js:80,92` |
| `debt` | `03-core.js:168` | 标的负债（并表时全额并入） | 无 | `05-firm.js:11`、`17-ledger.js:85` |
| `bankrupt` | `03-core.js:168` | 该持仓是否已破产 | `14-npc.js:171` | `05-firm.js:4`、`17-ledger.js:81` |
| `acquiredAt` | `03-core.js:168` | 收购时刻 | 无 | 无人读 |
| `navSnapshot` | **代码里从不写入** | 标的净资产快照 | 仅测试写（`tools/holdings.test.cjs` T8/T9） | `05-firm.js:10`、`17-ledger.js:85` |

> ⚠ **两条硬事实（本次实测）**：
> 1. **`stake` 在引擎里是死字段**。全项目 grep `stake` 只命中：`03-core.js:168`（写）、
>    `05-firm.js`（无）、`17-ledger.js:93`（UI 读来显示）。`consolidated()` 用的全是 `control`。
> 2. **`navSnapshot` 从不被生产代码写入**。它只在 `tools/holdings.test.cjs` 里被手工塞过。
>    ⇒ 任何"参股公司"的持股卡，家底都会显示 **0 G**（`17-ledger.js:85` 读 `h.navSnapshot || 0`）。

**合并报表的现口径**：`game/parts/05-firm.js:1-14`

```js
let nav = this.nav(p);                                  // ① 主控公司：走玩家自己的账（不乘任何比例）
let debt = (p.debt || 0) + this.shortLiability(p);
for (const h of hs) {
  if (h.corpId === p.corp) continue;                    // ② 主控公司在①已计，跳过
  nav += (h.navSnapshot || 0) * (h.control == null ? 1 : h.control);   // ③ 参股/控股：按 control 加权
  debt += h.debt || 0;                                  // ④ 标的负债全额并入
}
```

> ⚠ ①②合起来的后果：**主控公司是被"全额计入"的，不乘 `stake` 也不乘 `control`**。
> `04-ticks.js:287-292` 的注释承认了这点（"现阶段只有 1 条持仓且 control = 1，所以等价于旧的单公司口径"），
> `docs/19 §4.12` 开头也自己点破了（"`consolidated()` 里主控公司走 `this.nav(p)`、**根本不乘 stake**"）。
> ⇒ 这就是 `docs/19 §4.12` 说的"卖 30% 股份 = 印钞"那条推导的代码证据。

**并表数字的消费方**：
- 顶栏身价大字：`game/ui-parts/08-chrome.js:36`（`G.consolidated(HUMAN).nav`）
- 告急带/预警：`08-chrome.js:110`、`17-ledger.js:33`、`05-firm.js:33`（破产判据）
- 破产判据用的是 `maintRatio`：`01-data.js:74`（0.30）、`01-data.js:75`（`graceHours: 6`）

**命名地雷**：`07-metrics.js:18` 有一个 `controlMult`，**与治理的 `control` 毫无关系**
（它是"垄断溢价"，`controlMult(p, cid)` 按该作物的控盘度给最高 1.4 倍估值）。
新写治理代码时若再叫 `control*`，会与这个既有符号撞脸。

### 1.4 玩家与 NPC 的控股关系怎么存（结论：等于没存）

- 每个玩家对象都由同一个工厂函数创建：`03-core.js:157`（`_newPlayer`）→ `03-core.js:168` 恒为 **1 条、全资**。
- NPC 阵容：`03-core.js:222-231`（老陈/阿May/眼镜/坤叔/祥嫂/钱串儿），各自 `corp` 不同，**各自只持有自己那一家的 100%**。
- 唯一的"跨主体"痕迹是**破产接管**：`14-npc.js:185` `if (creditor) creditor.m.acquisitions++;`
  —— 只加了一个**计数**，没有真的把标的写进 `creditor.holdings`（同一函数 `14-npc.js:170-171` 只在本人的持仓上盖 `bankrupt`）。
- ⇒ **当前不存在"多家股东共同持有一家公司"的任何数据形态**。`docs/19 §4.13-A` 说名册"不需要新模型"（结构确实够用），
  但**名册现在恒只有 1 个人**，决议系统会空转（§3-C1）。

### 2.1 股东会职权与表决门槛

| 规则 | 现实内容 | 核实程度 |
|---|---|---|
| 股东会职权 | 选举/更换董事监事、审议批准董事会报告与**利润分配方案**、**增减注册资本**、**合并/分立/解散/清算**、**修改章程** | ⚠仅搜索摘要（搜狐·知恒定《公司法基本概念系列》 https://www.sohu.com/a/714228981_121223253 ；知乎《新《公司法》下"股东"20问20答》 https://zhuanlan.zhihu.com/p/716246200 ） |

| 一股一票 | 除优先股等特殊安排外，股东按**出资比例/所持股份**行使表决权 | ⚠仅搜索摘要（同上） |

### 2.2 30% 要约收购义务 + 权益变动披露（**这条有真实执法案例**）

**✅正文已抓取**：21世纪经济报道，2026-06-22《300亿羊绒巨头转型能源供应商，因股东治理问题被公开谴责》
https://www.21jingji.com/article/20260622/herald/c1faa3268b4fc26bec84ce53056e326d.html

> 上交所纪律处分认定：控股股东及一致行动人**在持股达到 30% 以上后，多次增持公司股票，
> 直至持股比例达到较高水平，均未按规定发出收购要约、履行豁免要约相关义务或履行权益变动披露义务**。
> 另一项认定是"**一致行动关系披露不准确**"（自 2010 年起通过集中竞价增持但未完整披露）。
> 报道同时点明："**一致行动人**……关系到投资者如何判断一家上市公司的控制权结构、股权集中度，
> 以及相关股东是否**触发收购义务**"；监管最终"**公开谴责**"并**记入诚信档案**。

⇒ 与本项目的关系（**可直接内化**）：
1. **30% = 必须公开叫价**这条不是理论，有真实处罚案例（`docs/19 §4.11-B` 的 30% 行）。
2. **"一致行动人" = 本项目天然的 `holdings` 聚合问题**：同一个玩家在多家公司/多个 shell 名下持股，
   该不该合并计算披露？（对应 `docs/19 §4.9` 的"风声"与皮包公司的隐蔽度）
3. **"每再增减 5% 再公告"**（`docs/19 §4.11-B` 的 5% 行）有现实对应（权益变动披露义务）。
4. **内化方向**：公告不是"给你加个弹窗"，而是**暴露代价**（隐蔽度↓ / 被别人盯上），
   正好接上项目已有的 `p.shell.cover`（`03-core.js:172`）。

### 2.3 优先购买权（ROFR）—— `docs/19 §4.14-B` 的核心

| 规则 | 现实内容 | 核实程度 |
|---|---|---|
| 优先购买权 | 股东向**股东以外的人**转让股权：**① 须其他股东过半数同意**；**② 不同意者应当购买**；**③ 同等条件下其他股东有优先购买权** | ⚠仅搜索摘要（多家律所/术语文章标题命中：旗渡法律翻译《投融资协议中的8个代表性核心术语——领售权/跟售权/优先购买权…》 https://www.qidulp.com/article/p/1168 —— 正文抓取返回空壳；条文编号待复核） |

⇒ 与本项目的关系：`docs/19 §4.14-B` 的三条（过半数同意 / 不同意应购买 / 同等条件优先）
**与现实表述一致**，可以直接作为实现规格。**本项目当前完全没有这条**（§3-C2）。

### 2.4 随售权 tag-along 与领售权 drag-along —— `docs/19 §4.14-C`

| 术语 | 现实内容 | 核实程度 |
|---|---|---|
| **领售权 / 拖售权（drag-along）** | **大股东**实现"100% 干净出售"的工具：约定的出售方接受第三方要约时，**可强制**其他股东以同等条件一起卖 | ⚠仅搜索摘要（Yeo Ashley《Drag-Along and Tag-Along: How They Actually Work》 https://www.yeoashley.com.my/article/drag-tag-mechanics/ ，摘要原文：`Drag-along is the majority's tool to deliver a clean 100% sale.`；浙江智仁律师事务所《投资协议解析｜出售权条款》 https://www.zhirenlawyer.com/zrjz/2822.html ） |
| **随售权 / 跟售权（tag-along）** | **小股东**的保护：大股东拟出售时，小股东可**主张以相同条件**把自己的股权一并卖给同一受让方 | ⚠仅搜索摘要（同上；摘要原文：`Tag-along is the minority's protection against being stranded under a new majority owner.`） |

⇒ 与本项目的关系：`docs/19 §4.14-C` 说这两条"与 §4.13 的 66.7% 特别决议天然咬合"，
**成立**：drag-along 的门槛应直接复用特决门槛（66.7%），tag-along 是**触发后的可选动作**而非独立决议。

### 4.1 股东名册数据结构

**只做"读"，不改 `holdings` 的既有形状**（`tools/holdings.test.cjs` T1 锁死了六字段）：

```js
/* 股东名册：从权威数据 holdings 派生，不落盘、不缓存（与 _mailTick 同一哲学：派生 > 插点） */
Game.prototype.capTable = function (corpId) {
  const rows = [];
  for (const p of this.s.players) {
    if (!Array.isArray(p.holdings)) continue;               // 旧存档兜底（对齐 05-firm.js:3-5）
    for (const h of p.holdings) {
      if (h.corpId !== corpId || h.bankrupt) continue;
      rows.push({ pid: p.id, name: p.name, stake: h.stake == null ? 1 : h.stake,
                  control: h.control == null ? 1 : h.control });
    }
  }
  return rows;                                              // [{pid, name, stake, control}]
};
```

- **`stake` 与 `control` 的分工（本次拍板建议，见 §4.3）**：
  - `stake` → **分红权 + 表决权**（"一股一票"）
  - `control` → **并表权重 + 进入经营 UI 的资格**（`≥0.5` 才解锁 7 页签，对齐 `17-ledger.js:104`）
  - ⇒ 两者**默认相等**；只有"双层股权/表决权委托"类玩法才让 `control !== stake`，**首批不做**。
- **必须补的写入点（否则名册只有自己）**：`navSnapshot` 要有人写。
  建议在 `_navTick`（`05-firm.js:76-88`，已有每 60 游戏分钟采样）里，
  对**非本人主控**的持仓回填 `h.navSnapshot = 该标的的 nav`。**收购层落地前，参股标的仍为 0 ⇒ 不要先做"参股转让"**（§5.3）。

### 4.2 决议生命周期状态机

```js
/* 新建容器（与 s.offers 并列，不塞进去） */
s.decisions = [];        // 决议
s.decisionsSeq = 0;

/* 一条决议 */
{
  i,                       // 序号
  corpId,                  // 在哪家公司表决
  kind,                    // 'sell'|'acquire'|'dilute'|'dividend'|'chair'|'invest'（docs/19 §4.13-D）
  type,                    // 'ordinary'(≥50%) | 'special'(≥66.7%)
  proposer,                // 发起人 pid
  topic,                   // 一段玩家可见的说明（走双名制）
  payload,                 // 议题参数（如 dividend: {ratio}；sell: {buyerPid, price}）
  openedT, deadlineT,      // 表决期（默认 s.t + 1440）
  board,                   // { pid: 'for'|'against'|'abstain' }  已投票
  base,                    // 计票基准：'stake'（见 §4.3）
  status,                  // 见下
  mails,                   // { pid: mailId }  送达记录
  result,                  // { forShare, againstShare, ratio, threshold } 计票快照
}
```

**状态机**：

```
        ┌────────────── 发起（≥10% 持股，docs/19 §4.11-B）
        ▼
      open ──(截止时计票)──┬─→ passed     （赞成占比 ≥ 门槛）
                           ├─→ rejected   （反对占比 ≥ 门槛）
                           ├─→ lapsed     （无人投出有效票 / 全员弃票）
                           └─→ deadlocked （赞成 == 反对且均未达门槛，本次作废）
```

- **`lapsed` 与 `deadlocked` 必须分开**：`docs/19 §4.13-C` 把"超时弃票"和"僵局"写成两种结果，
  但状态机里若合并，UI 就无法区分"没人理你"与"两边顶上了"（这是两封不同的回信）。
- **超时 = 弃票 = 中性**（`docs/19 §4.7`）：到期未投的股东**不计入任何一边**，
  但**其股份仍计入分母**（否则小股东集体不投票就能让决议自动通过）。
- **发起即扣款？不扣。** 决议本身不动钱；只有 `passed` 之后由各自的结算函数执行（对齐
  `15-auction.js:337-341` "提案本身不改任何状态"的既有纪律）。

### 4.3 计票规则（含"投票基准"拍板）

```js
/* 计票基准二选一，必须写死一个（本报告建议 A） */
A. 'stake'   —— 一股一票（docs/19 §4.13-C 原文口径）
B. 'control' —— 按控制权（docs/13 §7.2 的"双层股权"口径）

/* 计票 */
denom = Σ base(所有在册股东)                    // 弃票者计入分母，not 分子
cast  = Σ base(投 'for' 的股东)
ratio = cast / denom
threshold = (type === 'special') ? 0.667 : 0.5
passed = ratio >= threshold
```

**拍板建议：先用 A（`stake`）**，理由三条：
1. 与 `docs/19 §4.13-C` 原文"一股一票（权重 = 持股%）"一致，改动量最小；
2. `control` 在代码里**已经是并表权重**（`05-firm.js:10`），同时当表决权重会**一个字段两个语义**，
   而 `stake` 现在**完全闲置**——正好接上；
3. 平局规则才成立（`docs/19 §4.7` 的"票数平按股份占比"在 A 下恒等，可安全删除，见 C1-8）。

**平局**：`for === against` 且两者都 `< threshold` ⇒ `deadlocked`。
**边界**：`for` 恰好 `=== threshold` ⇒ **通过**（现实"三分之二以上"含本数）。

### 4.4 门槛判定（3/5/10/20/30/50/66.7% 的实现位置）

**统一成一个纯函数**，避免七道门槛散落七处（`docs/19 §4.11-B`）：

```js
Game.prototype.stakeTier = function (ratio) {
  if (ratio >= 0.667) return 7;   // 特别决议（改章程/增减资/合并分立/卖公司）
  if (ratio >= 0.5)   return 6;   // 普通决议说了算
  if (ratio >= 0.3)   return 5;   // 再买就得公开叫价（要约收购义务，见 §2.2 案例）
  if (ratio >= 0.2)   return 4;   // 可提名董事（只读 → 可看细节）
  if (ratio >= 0.1)   return 3;   // 可发起决议
  if (ratio >= 0.05)  return 2;   // 举牌：必须公告（暴露代价）
  if (ratio >= 0.03)  return 1;   // 可提交议题
  return 0;
};
```

- **跨线时要做的事（不能只算不做事）**：
  - **过 5%（含每 ±5%）** → 强制公告 ⇒ 接 `p.shell.cover`（隐蔽度↓）与信匣（"街面上都知道了"）
  - **过 30%** → 必须发要约：**禁止私下继续加仓**（`docs/19 §4.11-B`），UI 提示"再买就得公开叫价了"
  - **过 50%** → 解锁 7 页签（`17-ledger.js:104` 的 `control >= 0.5` 判据要改读 `stake`，见 §5.1）
- **门槛距离条**（`docs/20 §7` 的产物）：`stakeTier` 天然提供"距离下一档还差多少"。

### 4.5 哪些议题**必须先有公司现金独立账**（§4.12 前置）

`docs/19 §4.13-E` 已给结论，本次**核实并细化**：

| 议题 | 是否必须先有公司现金独立账 | 理由 |
|---|---|---|
| **卖公司** | ✅ **必须先有** | 否则交易对价会绕过公司账进个人账 ⇒ 和 §4.12 开头推的"卖股份=印钞"同一条路径 |
| **换掌舵人** | ✅ **必须先有** | 掌舵人拿的是**公司**薪酬（§4.17-A 的"薪酬"入口）⇒ 没有公司账，薪酬无处扣 |
| **减资** | ✅ **必须先有** | 减资是"把钱从公司退回股东"⇒ 公司没有独立现金，退的就是个人的钱 |
| **分红（派现）** | ✅ **必须先有** | 同上，且它本身就是 §4.12 定义的第一条合法通道 |
| 收购别家 | ❌ 不必 | 买方是个人（`p.cash`），标的的 `holdings` 由收购层负责 |
| 增发/稀释 | ❌ 不必（但**需要**股本概念） | 增发的钱进的是**标的公司**，属于收购层数据 |
| 重大投资（买地/开作坊） | ⚠ **建议一并接** | 现状是个人付钱买"公司资产"（`10-plot.js:2` 直接 `p.cash -= cost`）⇒ 这是 §4.8"资产绑公司"的反面 |

**落地顺序（沿用并强化 `docs/19 §4.13-E`）**：

```
   → §4.14 股份转让 + ROFR
   → 参股公司上的决议（无前置，但需要 navSnapshot，见 §4.1）
```
