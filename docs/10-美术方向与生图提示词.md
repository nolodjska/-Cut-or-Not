## 0. 工具参数确认（先看这个，全部经过实测或查证，不含猜测）

### 0.1 gpt-image-2 已确认的能力表

| 参数 | 可用值 | 怎么传 | 证据 |
|---|---|---|---|
| 模型 id | `gpt-image-2` | `-m gpt-image-2`（`gen.mjs` 的默认值就是它） | `scripts/models.json` → `image["gpt-image-2"]` |
| `quality` | `medium` \| `high`（默认 `medium`） | `--quality high` | 同上 + `gen.mjs --help` |
| `resolution` | `1k` \| `2k` \| `4k`（默认 `1k`） | `--resolution 2k` | `--dry-run` 回显 `"resolution": "2k"` |

| 提示词上限 | 图片模型未列出 `prompt_max`（视频模型才是 10000） | — | `models.json` 只有 video 段有 `prompt_max` |
| 独立负向字段 | **不存在** | 负向词只能写进 prompt 正文 | `references/api.md` L54-55 的字段白名单里没有 negative |
| 结果 URL 有效期 | 约 15 分钟，签名 URL | 脚本会自动下载到本地 | `references/api.md`「Download promptly」 |

### 0.2 七条被证伪的常见假设（照这些假设写提示词会白花钱）

## 1. 调性与视觉概念

### 1.1 一句话

> **一块被搬进深夜行情终端的菜地：土是暖的，屏是冷的，结算时全场镀金。**

不是赛博朋克，不是萌系农场，也不是大厂 SaaS 的扁平插画。它更像**一本被放在乡政府会议桌上的手写账本，旁边立着一台旧显示器**——质感是粗糙的、纸的、泥的，光是半夜的、单一方向的、吝啬的。玩家要在 3 个游戏天里从种萝卜变成逼仓，画面必须同时容得下「刚拔出来的萝卜上的土」和「屏幕上一段折线」。

### 1.2 三个温度（这是整套视觉的结构）

| 温度 | 对应 | 色域 | 在画面里的占比 | 在哪里出现 |
|---|---|---|---|---|
| **土（暖）** | 农事、作物、木头、麻袋、账页 | 土棕 `#6b4f33` / 麦秆黄 `#c9a069` / 叶绿 `#5aa863` | 约 8% | 农田页、作物图标、事件插图、开局横幅 |
| **屏（冷）** | 行情、情报、钱庄、拍卖 | 冷蓝 `#4aa8ff` / 紫 `#a97bff` / 涨绿 / 跌红 | 约 2%（纯色块很小，但**最高饱和度**在这里） | 市场页曲线、情报页、拍卖页、所有数据 |
| **金（贵）** | 结算、颁奖、首席、成交 | 金 `#f5c451` | **≤2%，且必须吝啬** | 只允许出现在：结算页首席卡、拍卖成交瞬间、App 图标、分享卡上的奖章 |

**配比规则（可验收）**：暗底 ≥ 88%，土系 ≤ 10%，金 ≤ 2%。金一旦超过 2%，结算页「镀金」的意义就没了——金是奖励，不是主题色。

> ⚠ **本条已于 2026-10-08 被用户授权解除**（原话：「批准你可以无视 doc/10 的说法，对他进行修改，因为这是 demo 的标准，我们准备做大，所以可以无视」）。
v2 的基底改为**牛皮纸（暖，~85%）**，冷色收进「屏」内嵌面板（~13%），金仍 ≤2%。
**新的权威文档见 `docs/12-复古农商视觉改版.md` §2、§3。** 本条的意图（三个温度、金必须吝啬）仍然有效，只是占比被重新分配。

**仍不得违反的**：`07` §2.8.3 的审核红线（不得出现 `¥ ￥ $ 元 人民币`；不得使用与证券软件明显同款的涨跌红绿样式；不得出现站外二维码）。

**扩展色（只有 3 个，全部属于「土」域，不得用于数据）**

| 名称 | 色值 | 用途 |
|---|---|---|
| 土棕 | `#6b4f33` | 土壤暗部、木箱、麻袋、青铜（**也是奖章的主色**） |
| 麦秆黄 | `#c9a069` | 干草、纸页、作物受光面、面包与碗 |
| 叶绿 | `#5aa863` | 茎叶、幼苗（**与 `--up` 的荧光绿必须能一眼分开**） |
| 幕布红（仅 1 处） | `#7a2f2a` | **只允许用于颁奖礼的背景幕布**，全站唯一饱和红 |

**语义色 / 自然色分离规则（这套视觉最重要的一条硬规则）**

- `--up #35d07f`、`--down #ff5c5c`、`--gold`、`--accent`、`--purple` 是**语义色**：只用于数据、按钮、状态，**永不用于自然物**。
- 土棕 / 麦秆黄 / 叶绿 / 幕布红是**自然色**：只用于插画，**永不用于数据**。
- **辣椒是这套规则最尖锐的用例**：辣椒本体是红的，而 `--down #ff5c5c` 是「跌」。若辣椒插画画成 `#ff5c5c`，玩家会把「辣椒」直接读成「下跌信号」。**裁定：辣椒用晒干的红 `#a84a3c`（自然色域），且必须带土棕暗部**，绝对不用 `#ff5c5c`。
- 同理，萝卜的绿缨用 `#5aa863`，绝不用 `#35d07f`。

### 1.4 字体建议（中文移动端，按可实现性排序）

| 位置 | 字体 | 落地方式 | 成本 |
|---|---|---|---|
| 全部中文 UI 与正文 | 现有栈不改：`-apple-system, BlinkMacSystemFont, "PingFang SC", "Hiragino Sans GB", "Microsoft YaHei"` | 已在 `game/index.html` 的 `body` | 0 |
| 所有金额与数字 | 同栈 + `font-variant-numeric: tabular-nums` | 已有 `.mono` 类（`font-feature-settings:"tnum"`） | 0 |
| 结算页称号大字 / 首席名 | **思源宋体（Noto Serif SC / Source Han Serif SC）子集 woff2**，只裁「首席胜利者/农业大亨/不倒翁/市场霸主/准市场霸主/全能商人 + 10 个提名名 + 常用 30 字」 | 仅结算页 `@font-face` 按需加载，`font-display: swap` | 约 6 KB，可接受 |

### 1.5 图形语言

| 维度 | 规定 | 理由 / 验收 |
|---|---|---|
| **描边** | 有。细的深棕墨线（比 `#0b0f14` 略暖），交付尺寸 96px 时约 1.5px，放大时线性变粗 | AI 无法精确控制像素，所以 prompt 只写 `thin dark walnut ink outline`，验收时看「缩到 96px 是否还看得出轮廓」 |
| **噪点/颗粒** | 有，轻。冷压纸颗粒 + 轻微噪点 | 上限：在 96px 缩略图上**不应看见明显雪花点**。噪点过重会在深底上显脏，且压缩后变成色块 |
| **图标风格** | **单主体 + 无场景**。一张图只允许一个视觉焦点，禁止「图标里再套小图标」 | 96px 下多物体必糊。这直接决定了「作物图标」和「作物插画」是两套资产，不是一套缩放 |
| **立体感** | 手绘数字水粉（digital gouache），浅浮雕级别明暗；**禁止 3D 渲染光泽、禁止塑料高光、禁止倒影地板** | 3D 光泽会让「市场是绞肉机」的冷幽默变成玩具广告 |
| **视角** | **全站只有两个视角**：物件类 = 俯角 40° 四分之三视角；场景类 = 相机高约 60~80cm 的平视（地平线/桌沿落在画面下三分之一） | 视角不统一是「拼贴感」的第一来源。禁止俯拍、仰拍、鱼眼、等距（isometric） |
| **光线** | 全站固定：**左上主光**（暖或中性）+ **右侧冷蓝轮廓光**（`#4aa8ff` 的暗版）。夜景只有两个光源 | 固定光位是让 35 张图看起来像一套的最省力手段，也比 style 词更有效 |
| **留白** | 物件类四周 ≥ 20% 空边；场景类**上三分之一必须是暗部且可压字** | 直接服务于 §5 的「方形深底图放进卡片」方案，省掉整条抠图管线 |
| **剪影测试** | 任何资产缩到 48px 后，主体剪影必须仍可辨认 | 奖章、App 图标、作物图标的统一验收闸门 |
| **禁止元素** | 不画人脸、不画面部、不画有眼睛的吉祥物、不画二维码、不画文字数字、不画货币符号、不画真实公章/国徽 | 前四条是调性，后三条是 `07` 的审核红线与文案红线自动检查的盲区（烧进图里的字逃过 `lint-copy.cjs`） |

### 1.6 三条「绝不这么做」

**① 绝不做霓虹赛博朋克。**
不要黑底荧光紫绿、不要 holographic 渐层、不要发光网格、不要故障艺术（glitch）、不要满屏发光 K 线柱。
理由：这款游戏讲的是「同学之间互相坑」，一个币圈广告的视觉会把它读成「这是炒币」；而且 `07` §2.8.3 明确点名「不得使用与证券软件明显同款的涨跌样式」，霓虹 K 线正好踩线。

**② 绝不把文字、数字、货币符号、二维码烧进图。**
包括：中文标题、价格数字、`¥ ￥ $ 元`、Logo 字标、二维码、图表轴标签。
理由：三个叠加的后果——(a) gpt-image-2 画中文必糊，返工率最高；(b) 烧进图里的字**逃过** `tools/lint-copy.cjs` 的自动红线检查，等于给审核埋雷；(c) `¥ ￥ $ 元` 是明文禁令。**所有文字一律由 HTML 层渲染**，图只负责画东西。

**③ 绝不做拟人化吉祥物。**
不要大眼睛萝卜、不要会笑的辣椒、不要给作物加手脚、不要「可爱版」首席奖杯。
理由：「市场是绞肉机，拍卖是屠宰场，结算是一场颁奖礼」是冷幽默，不是亲子农场；而且现有代码的降级方案就是 emoji（🥕🌶️🌿），拟人形象会和 emoji 抢同一角色，导致正式资产与降级态两套形象并存、互相拆台。

## 2. 资产清单

### 2.1 总表

尺寸列 = **交付尺寸**（给 H5 用的实际文件）。生成档位见 §3，两者不同。
「透明」列已按 §0.2 第 1 条重新裁定：**gpt-image-2 不支持透明背景，所以设计目标是把「需要透明」压到最少。**

| 编号 | 名称 | 用途（页面 · 位置） | 交付尺寸 | 需透明 | 优先级 |

## 3. 生图提示词

### 3.0 怎么用（先把这一节读完，再抄下面的 prompt）

**命令模板**（`gpt-image-2` 默认就是 `gen.mjs` 的图像模型，`-m` 可省但建议显式写）：

```bash
node scripts/gen.mjs -m gpt-image-2 \
  -p "<把下面 fenced block 里的整段 prompt 原样粘进来>" \
  --quality high --resolution 1k --aspect 1:1 \
  -o "assets/raw/A01-radish-icon-1.png"
```

四条纪律：

1. **一张图 = 一次请求**（§0.2 第 2 条）。下面的「出 N 张」都指 N 次独立请求，文件名带 `-1/-2/-3`，挑中后重命名为 `assets/<key>.png`（key 用 §5.5 的映射表 key，前后端对齐）。
2. **迭代在 1k，定稿才升档**。任何资产先按文档档位出一张，确认构图后再出第二三张。
3. **prompt 存文件再批量跑**：建议把每条 prompt 存成 `assets/prompts/A01.txt`，这样 prompt 可版本管理，重跑不用复制粘贴：
   ```bash
   for f in assets/prompts/*.txt; do
     n=$(basename "$f" .txt)
     node scripts/gen.mjs -m gpt-image-2 -p "$(cat "$f")" \
       --quality high --resolution 2k --aspect 16:9 -o "assets/raw/$n-1.png"
   done
   ```
4. **不要手写 `--idem`**。脚本每次自动生成新 key；手写同一个 key 配不同 body 会拿到 `409 MEDIA_TASK_IDEMPOTENCY_CONFLICT`。

**§3 所有 prompt 的两个固定构件**（下面每条都已经把这两段拼在正文里，所以整段复制即可；单独列出是为了日后统一微调）

**S1 — 物件类固定风格尾**（图标 / 徽章 / 奖章 / App 图标）：
> `hand-painted digital gouache on cold-press paper, fine paper grain, thin dark walnut ink outline, very dark desaturated navy background #0b0f14 with a soft corner vignette, one soft key light from the upper left and a faint cold blue rim light from the right, subject centered with generous empty margin on all sides, palette strictly limited to bronze and soil brown #6b4f33, straw ochre #c9a069, leaf green #5aa863, signal gold #f5c451, cold blue #4aa8ff`

**S2 — 场景类固定风格尾**（事件 / 拍卖 / 颁奖 / 分享卡 / 开局横幅）：
> `hand-painted digital gouache on cold-press paper, fine paper grain and a light dusting of noise, thin dark ink outlines, night scene lit by exactly one warm amber source and one cold blue source, deep desaturated navy shadows #0b0f14, soft haze in the air, camera at knee height looking straight ahead, horizon or floor line on the lower third, the upper third of the frame left dark and empty for interface text, palette strictly limited to soil brown #6b4f33, straw ochre #c9a069, leaf green #5aa863, signal gold #f5c451, cold blue #4aa8ff`

**N1 — 固定负向尾**（gpt-image-2 无独立负向字段，只有拼进 prompt；因为模型对「不要 X」的服从度有限，N1 里的每一条在 §4.4 的验收闸门里都有对应的人工检查）：

## 4. 一致性保障

### 4.1 六个机制（按重要性排序）

| # | 机制 | 具体做法 | 为什么它比「写好 style 词」有效 |
|---|---|---|---|
| 1 | **母版派生** | 先出 A00（4 张挑 1），上传公网，其余 34 张全部加 `--ref <A00 公网 URL>`（`reference_images: true` 已确认，可多张，保守起见一次 ≤ 3 张） | 参考图传递的是模型学到的「这张画的画法」，比形容词精确得多 |
| 2 | **统一生成底色 `#0b0f14`** | 所有资产的背景色都用页面底色，不用面板色 `#131a22` | 一箭双雕：既统一了氛围，又让「方形图放进卡片」不需要抠图（§5.1）。若用面板色当底，放进卡片就是同色，放进页面就是一块块方砖 |
| 3 | **固定光位** | 左上暖主光 + 右侧冷蓝轮廓光，全站不变 | 光位不一致是「拼贴感」的头号来源，且它比色板更容易被模型稳定执行 |
| 4 | **固定视角** | 物件类 = 俯角 40° 四分之三；场景类 = 相机 60~80cm 平视 | 同上。禁止俯拍/仰拍/等距 |
| 5 | **固定后缀 S1/S2 + 固定负向 N1** | 见 §3.0，逐字复用，不即兴改词 | 减少变量。任何一张想要「再好看一点」而临时加词的图，都会变成这套里唯一一张不像的 |
| 6 | **参考图之外的二次校正** | 若整批偏色，用同一条命令批量校正（示例：`magick mogrify -modulate 100,88 asset/*.png` 降 12% 饱和），或在 CSS 层统一 `img.asset{filter:saturate(.92)}` | 模型的色偏是批量的、一致的，所以校正也可以批量做。CSS 那一版只改一行、可回滚 |

### 4.3 批次纪律（这些在整个批次里不许改）

| 不许改 | 原因 |
|---|---|
| 模型（全程 `gpt-image-2`） | 混用 `nano-banana-pro` 会得到另一套笔触；`models.json` 里三个模型风格不同 |
| `quality` 与 `resolution` 组合（同批内） | 同批内混档会让细节密度不一致，缩到小尺寸后一眼看得出 |

| 光位与视角 | 同上 |
| 中途「只给这一张加点新东西」 | 唯一允许的例外是 §3 里已写明的「各资产的主体句差异」与「事件/资产专属负向」 |

### 4.4 验收闸门（每批产出后逐张过，四条）

| 闸门 | 检查方法 | 不通过的后果 |
|---|---|---|
| **① 文字闸门** | 放大到 200% 逐张看：有没有出现字母、数字、字、二维码、货币符号 | 有字就退稿重跑——烧进图里的字逃过 `lint-copy.cjs`，且违反 `07` §2.8.3 |
| **② 留白闸门** | 场景类：上三分之一是否真的能压白字（用手机把白字贴上去看）；物件类：四周空边是否 ≥ 20% | 留白不足的图在页面上会和 UI 打架，是「看起来很挤」的真正原因 |
| **③ 剪影闸门** | 缩到 48px（物件）或 300px 宽（场景）后是否仍可辨认 | 认不出就等于白做——玩家在手机上只看到这个尺寸 |
| **④ 色板闸门** | 取色器抽查主体与背景；辣椒类必须确认**没有 `#ff5c5c`**；金色占比 ≤ 2%（结算类除外） | 出 `#ff5c5c` 的辣椒会被读成「下跌信号」，直接推翻 §1.3 的语义/自然色分离 |

## 5. 落地与性能

### 5.1 从 PNG 到 H5 资产：一条不抠图的管线

因为 gpt-image-2 **不支持透明背景**（§0.2 第 1 条），抠图是唯一能拿到 alpha 的路，而 AI 抠图在 96px 上必然有毛边。所以：

> **方案：放弃抠图，改用「深底方形图 + 圆角容器」。**
> 所有资产都以 `#0b0f14` 为底生成，放进页面时用一个容器铺同色底并加圆角：
> ```css
> .asset{background:#0b0f14;border-radius:var(--r);display:block;object-fit:cover}
> .asset.sq{border-radius:10px}
> .asset.circle{border-radius:50%}   /* 奖章与徽章用这个，圆形裁切不需要 alpha */
> ```
> 面板是 `--panel #131a22`，资产底是 `--bg #0b0f14`，两者本身就差一档明度——这正是想要的「图是嵌进卡片里的一扇窗」的效果，不是缺陷。

**六步工序**：

| 步 | 动作 | 工具/命令 | 输出 |
|---|---|---|---|
| 1 | 生成（§3 的档位，2k 产出） | `node scripts/gen.mjs ...` | `assets/raw/A01-1.png` |
| 2 | 挑选（过 §4.4 四道闸门） | 肉眼 + 取色器 | 挑中的一张 |
| 3 | 裁切（按目标比例兜底裁） | `magick A01-1.png -resize 512x512^ -gravity center -extent 512x512 A01.png` | 方形/比例正确 |
| 4 | 缩放到交付尺寸 | `magick A01.png -resize 288x288 -quality 82 A01.webp` | WebP |
| 5 | 转 WebP + 体积检查 | `magick identify -format "%f %wx%h %b" *.webp` | 每张不超标（见 §5.2） |
| 6 | 命名与归档 | 重命名为 `assets/<key>.webp`，key 见 §5.5 | 待接入 |

**格式裁定**：统一 **WebP（有损 q78~q85，无 alpha）**。
理由：可无损/有损统一、体积约为 PNG 的 1/4~1/3，iOS 14+ 与所有现代安卓 WebView 都支持；由于我们不需要 alpha，PNG 的唯一优势（alpha）消失。保险做法：图标类（A01-A03、A10-A13）体积已 <10 KB，可直接用 PNG-8，避免任何 WebP 兼容疑虑；场景类（>30 KB）一律 WebP。

### 5.3 加载策略（三条硬规则）

1. **首屏只加载「进游戏就看得到」的 8 张**：A01-A03（农田/市场图标）、A10-A13（开局选公司）、A54（开局横幅）。其余一律懒加载。
2. **预取要挑时机，不要用 `<link rel=prefetch>` 撒网**：奖章在「赛季进度 > 80% 且非省流量模式」时预取；事件图在「首个事件触发预告时」预取下一张。判断依据用现成的 `s.t / (BAL.days*1440)`（顶栏 `#dayfill` 已经在用它算进度）。
3. **`loading="lazy"` + `decoding="async"` 是默认值**，除了首屏那 8 张；图片一律给 `width`/`height` 属性，避免布局抖动（`.aw`、`.crop` 卡片会因此跳动，很难看）。

### 5.4 单文件 vs `assets/` 目录（需要改 `tools/build.mjs`，本文档不动代码）

| 路线 | 做法 | 优点 | 缺点 | 建议 |
|---|---|---|---|---|
| A：全部内联 base64 | 现有单文件交付不变 | 双击即玩、零请求 | 图片 base64 后 **+33% 体积**，且首屏把 148 KB 和所有图一起下 → 首屏膨胀到 1 MB 级 | **否** |
| B：`assets/` 外链（推荐） | `dist/` 拆成 `割不割-demo.html` + `assets/*.webp`；`build.mjs` 增加一步「复制 assets 到 dist」 | 懒加载可行、体积可控、可缓存、可按需替换单张图 | 不再是单个文件；本地双击需同目录有 `assets/`（`file://` 下相对路径图片可正常加载） | **是** |
| C：混合 | 只把 **< 10 KB 的图标**（A01-A03、A10-A13，共 56 KB）内联为 data URI，其余走 `assets/` | 首屏少 7 个请求，图标随 HTML 立即渲染 | 两套机制，构建稍复杂 | 折中可选，收益有限 |

路线 B 的落地细节（供改 `build.mjs` 时参考）：现有 `build.mjs` 已经会「内联失败就报错退出」，加一步 `fs.cpSync('assets','dist/assets',{recursive:true})` 并在 `ui.js` 里用相对路径 `assets/A01-radish.webp` 即可；`preview.html` 用 iframe 指向 `割不割-demo.html`，相对路径天然可用。

/* 资产兜底：图挂了就落回 emoji/单字，不让页面出现破图。

## 6. 待决问题

编号 `Q-ART-*`，格式与 `QUESTIONS.md` 保持一致（问题 / 为什么必须人定 / 推荐默认 + 备选 + 后果）。

**Q-ART-01｜视觉概念选「农事纪实 + 终端冷光」，还是更「数据流」？**
- 现状：本文档 §1.1 定的是「一块被搬进深夜行情终端的菜地」，土 8~10%、金 ≤2%。
- 为什么必须人定：这是整套资产的锚，定错方向要重跑 80 次请求（≈ $12 + 半天）。
- 推荐默认：**农事纪实 + 终端冷光**（现在这版）。理由：原案 §12.2 明写「股票知识要隐形，玩家先觉得好玩，再发现原来这是 K 线」——先给土，后给屏。
- 备选 A：更冷更数据化（把土降到 4~5%，让屏幕成为主体）。后果：更像金融工具，`07` 的证券样式禁令风险上升，且与 emoji 降级态的风格差距拉大。
- 备选 B：更暖更农事（金提到 5%）。后果：结算页的「镀金」不再稀缺，颁奖礼的仪式感被日常稀释。

**Q-ART-02｜要不要引入角色形象（NPC 头像、作物拟人）？**
- 现状：A55-A57（NPC 头像）列为 P2；§1.6 第 3 条禁止拟人吉祥物。
- 为什么必须人定：一旦有角色，所有场景图都要有角色出场，成本翻倍，且要回答「画不画脸」。
- 推荐默认：**不做拟人作物；NPC 头像维持 P2，且即使做也只画背影/剪影/无面孔**。理由：市场是绞肉机，拟人化会削弱「被割」的刺痛感。
- 备选：给 3 个 NPC 做半身头像（有脸，风格化）。后果：`07` 未禁止，但会立刻需要在结算页替玩家生成形象，工作量外溢到「捏人系统」。
- 备选：完全不做角色，NPC 只用颜色块 + 名字。后果：省事，但结算页「被记住」的满足感少一档。

**Q-ART-03｜首轮预算与批次怎么定？**
- 现状：§2.2 估 80 次请求 ≈ $11.5，含 50% 返工 → ≤ $20。
- 为什么必须人定：花的是真钱，且 `1k` 与 `2k` 差 2 倍价钱；`image_count` 只能 = 1，无法批量试错。
- 推荐默认：**先跑「批次 0 + 批次 1」（母版 + 7 类图标/徽章），$2.9 内验证风格，确认后再放批次 2~4**。理由：母版错了，后面全是废图。
- 备选 A：一次性全跑（省时间，$11.5）。后果：若母版风格不合意，24 张图全废。
- 备选 B：只跑 P0（$7 左右）。后果：P1 的 3 张作物插画与分享封面会缺，分享卡上没有作物图。

**Q-ART-04｜透明背景怎么办：抠图还是方形卡内嵌？**
- 现状：`gpt-image-2` 不支持透明（§0.2 第 1 条）。§5.1 推荐「深底方形图 + `.asset` 圆角容器」，完全不抠图。
- 为什么必须人定：这决定了要不要建一条抠图管线（多一个工具、多一道毛边风险），也决定生成底色。
- 推荐默认：**方形内嵌 + 统一底色 `#0b0f14`**，只有奖章与徽章用 `border-radius:50%` 裁圆（CSS 裁切，不需要 alpha）。
- 备选 A：本地抠图拿真 alpha（`rembg` 等）。后果：图标能做到真正的自由布局，但 96px 上的毛边几乎必然可见，且多一道工序。
- 备选 B：改用别的模型出透明图。后果：与 `gpt-image-2` 混用会破坏 §4.3 的批次纪律。

**Q-ART-05｜图片内联进单文件，还是拆出 `assets/`？**
- 现状：`dist/割不割-demo.html` 现在是单文件（148 KB）。§5.4 列了三条路线。
- 为什么必须人定：这是交付形态的变化（「双击一个文件就能玩」是 README 的卖点），并且要改 `tools/build.mjs`。
- 推荐默认：**路线 B（拆分 `assets/`）**，首屏 8 张必需图，其余懒加载。理由：base64 内联会让首屏膨胀到 1 MB 级，直接违背放置游戏「点开就玩」的体验。
- 备选 A：维持单文件、全部内联。后果：首屏 ≈ 1 MB，4G 下 4 s+，且以后每加一张图都更慢。
- 备选 C：混合（<10 KB 图标内联）。后果：首屏省 7 个请求，收益有限但可接受。

**Q-ART-06｜要不要为结算页引入中文字体（宋体子集）？**
- 现状：§1.4 推荐思源宋体子集约 6 KB，仅结算页加载；备选是全系统字体。
- 为什么必须人定：多一个字体文件与一次请求，且字体授权与加载失败态都要有人拍板。
- 推荐默认：**引入（仅结算页 `@font-face`，`font-display:swap`）**。理由：结算颁奖礼是本作最大差异化，「称号」用宋体比黑体更像一张奖状。
- 备选：全系统字体 + `letter-spacing:.05em`。后果：零成本零风险，但结算页少一层仪式感。
- 备选：全局换字体。后果：不推荐——重排风险高，正文可读性反而下降。

**Q-ART-07｜十枚奖章一次做完，还是先做 4 枚高频的？**
- 现状：§3.5 要求 10 枚成套（触发率从 94% 到 0.8%），成本 $2.0。
- 为什么必须人定：这是「成套 vs 分批」的取舍，牵扯到会不会在结算页露 emoji 降级。
- 推荐默认：**10 枚一次做完**。理由：结算页会同时出现多枚，混着单字圆章和插画奖章会显得像做了一半；且 $2.0 相对于「唯一卖点」不算钱。
- 备选 A：先做 4 枚高频（共同体/产业链/定海神针/隐形操盘手，覆盖 ≥82%）。后果：省 $1.2，但 4 枚稀有提名一旦触发就露兜底态（低频不等于不触发，`09` §3.3 证明 10 枚都会触发）。
- 备选 B：给稀有提名做特殊材质（金环）。后果：视觉上区分了稀有度（可能是好事），但违背 §4.3「一套金属」的纪律，需要重跑高频 4 枚。

**Q-ART-08｜插画里允许出现人吗？**
- 现状：§1.5 与全部 prompt 的负向都写了 `no human face, no human body`；A26 只允许画手。
- 为什么必须人定：这不是能力问题而是调性问题。「同学互相坑」需要有「人」的味道，但画了脸就要画一套人物设定。
- 推荐默认：**只有手、背影与影子，永远不画脸**。理由：无脸让玩家把自己代入进去；也躲开了「画得像某个同学」的社交风险（这是要发到微信群的游戏）。
- 备选 A：允许小比例出现无脸远景人形。后果：需要额外控制「谁是人、谁是 NPC」，成本上升。
- 备选 B：全部不出现人（连手也不画）。后果：A26 抢购潮失去主体，那张图要重设计。

**Q-ART-09｜七个事件是否都配图？**
- 现状：`engine.js` L188-194 有 7 个事件（干旱/丰收/带货/病虫害/政策/补贴/抢购），权重 3/3/3/2/2/2/1。
- 为什么必须人定：抢购潮权重只有 1（最罕见），补贴没有持续时间（`durH:0`），这两张图的使用频率明显低于其它五张。
- 推荐默认：**7 个全配**（$2.8）。理由：事件图是市场页最显眼的横幅，缺一张就会在那一天露出纯文字横幅，违和感很强。
- 备选：只配权重 3 的三个（干旱/丰收/带货，$1.2）。后果：省钱，但病虫害（会导致减产 50%，是逼仓机会）反而是战略上最该被看见的事件。
- 备选：不配图，继续用 `.banner`。后果：市场页少一层信息冲击，但零成本——这是当前代码的现状。

**Q-ART-10｜分享卡上要不要二维码？**
- 现状：`07` §2.8.3 明写「小程序内不得出现站外二维码」，本文档 A50 的负向写死 `no QR code`。
- 为什么必须人定：这不只是美术问题，是发布渠道问题——H5 官网版带二维码可以拉新，小程序版是红线。
- 推荐默认：**图里不画二维码；把二维码留给 HTML 层按渠道动态控制**（小程序构建不带、H5 构建带）。理由：图是死的、规则是变的，把可变元素交给代码。
- 备选：图里烧一个二维码角标。后果：小程序版必须整张重出，且违红线。
- 备选：完全不做二维码。后果：分享拉新全靠标题，转化率可能低一档。

**Q-ART-11｜App 图标是否就用「镰刀 + 折线」这个方案？**
- 现状：A51 的方案是「金色镰刀，刀身续成折线，最高点断开」。
- 为什么必须人定：图标是唯一会被反复看到 1000 次的资产，且它是品牌，改一次全渠道都要换。
- 推荐默认：**就用这个**。理由：它在 48px 下依然成立（§4.4 剪影闸门），且不用任何文字就讲清了「割不割」；金色占比可控。
- 备选 A：一根萝卜的剪影 + 一条折线。后果：更「农事」但更容易和一堆农场游戏撞脸，且「割」的动作感丢了。
- 备选 B：把「割不割」三个字压进图标。后果：48px 下必糊，且触发 §1.6 第 2 条。

**Q-ART-12｜要不要做亮色（日间）皮肤？**
- 现状：全部资产与现有 CSS 都是暗色单套（`--bg #0b0f14`）。
- 为什么必须人定：双皮肤意味着 35 张资产全部要出第二版（+$11.5），或接受「亮色皮肤配暗色图」的割裂。
- 推荐默认：**只做暗色**。理由：调性靠「深夜行情终端」立住，亮色会把「绞肉机」变成「周六农场」；且 §5.2 的首屏预算已经排满。
- 备选：只给农田页做亮色（白天种地 / 夜里看盘，正好呼应 §1.1）。后果：机制上有趣，但 3 作物图标 + 事件图需要第二版（+$3 左右）。
- 备选：不做皮肤，改用「白天/黑夜随游戏内时间渐变 CSS 变量」。后果：零新增资产，纯 CSS，但暗色图会在亮背景上显得像贴纸。
